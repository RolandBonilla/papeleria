# Evaluación de calidad ISO/IEC 25010

Autoevaluación del desarrollador sobre el estado actual del proyecto. Los niveles (Alto, Medio, Bajo) se justifican con evidencia que se puede comprobar en el repositorio. No se realizaron pruebas con usuarios reales ni auditorías externas.

| Característica | Nivel | Justificación (evidencia) | Limitaciones |
| --- | :-: | --- | --- |
| Adecuación funcional | **Alto** | Los 12 RF están implementados y probados (ver `docs/requirements.md`). El total se calcula con `Decimal` y centavos enteros; la venta rechaza cantidades mayores al stock. CP-01, CP-02 y CP-03 pasan. | Solo se valida el formato de la cédula, no su dígito verificador. No hay anulación ni devolución de ventas. |
| Usabilidad | **Medio** | Interfaz simple de 6 pantallas, mensajes de error en español y estados de stock con etiquetas de texto. Hay foco visible, etiquetas en los campos y diseño que se adapta al móvil. | No se hicieron pruebas con usuarios ni auditoría de accesibilidad. No hay búsqueda de producto dentro de la pantalla de ventas (se elige de una lista). |
| Fiabilidad | **Medio** | Las ventas se guardan en una transacción (todo o nada), probado en `test_venta_con_varios_productos_es_atomica`. Claves foráneas activas, validación de datos y 69 pruebas automáticas. | SQLite en un solo archivo: sin respaldos automáticos ni replicación (RNF-04 depende de mantener el servidor encendido). No hay pruebas de concurrencia ni de carga. |
| Seguridad | **Medio** | Contraseñas con PBKDF2-SHA256 y sal aleatoria; tokens firmados con HMAC y vencimiento; permisos por rol verificados en el servidor y probados (401/403); entradas validadas; el frontend escapa el texto que muestra. | Clave de firma por defecto para desarrollo (debe cambiarse); no hay HTTPS, límite de intentos de login ni revocación de tokens; el token se guarda en `localStorage`; las contraseñas de prueba son públicas. |
| Mantenibilidad | **Alto** | Tres capas con responsabilidades separadas, funciones pequeñas, patrones documentados, lógica de cálculo aislada y probable sin base de datos, CI que ejecuta las pruebas en cada push. | No hay análisis estático (linter) ni medición de cobertura. El frontend no tiene pruebas automáticas. No se usan migraciones de base de datos (solo `create_all`). |
